NameMapDraw
Syntaxmapdraw [id:<#>/new:<world>/undo:<key>] (pixel/dot/line/rectangle/fill/floodfill/image:<image>) (x:<#>) (y:<#>) (to_x:<#>) (to_y:<#>) (radius:<#>) (width:<#>) (height:<#>) (color:<color>) (record:<key> (begin)) (send:<player>|...)
Short DescriptionDraws directly into a map's vanilla pixel data.
Full DescriptionWrites straight into the map's own color array, the same one vanilla uses and saves.

This is deliberately not the Command:map command: that one attaches a Denizen map renderer,
whose objects are re-rendered in full on every change, are written into maps.yml, and grow without bound.
For a map that is drawn on many times - a player-painted canvas, for example - that does not scale.

Because the drawing lives in the map's vanilla data, it is saved and reloaded by the game itself
(in "world/data/map_<id>.dat"), so no separate storage, image file or renderer is needed.

Do NOT use the "map" command on a map drawn by this command: the Denizen renderer it attaches
renders once, caches the result and stops looking at the vanilla data, freezing the picture.

Maps drawn on this way should be given to players with "map_locked=true". Without it, vanilla
rescans the terrain into the map whenever a player holds it, wiping the drawing.

Maps are always 128x128, with 0,0 at the top left corner. Anything outside is clipped away.

Colors are matched to the map palette, which is fairly limited - the drawn color will be the
closest one available. Fully transparent input is skipped rather than drawn.

The shapes are:
- "pixel" sets a single pixel at x,y.
- "dot" fills a disc centered on x,y, covering every pixel within 'radius' (radius 0 is one pixel).
- "line" drags a 'radius' sized dot from x,y to to_x,to_y, for joining up sparse input into a stroke.
- "rectangle" fills 'width' by 'height' pixels starting at x,y.
- "fill" covers the entire map, ignoring x/y.
- "floodfill" recolors the connected area of same-colored pixels around x,y, like a paint bucket.
- "image:<image>" draws an ImageTag with its top left corner at x,y.

Specify "new:<world>" instead of an id to create a fresh map, which is then drawn on the same way.

Specify "record:<key>" to make the change undoable. Every pixel the command changes is remembered, with its
previous color, in the key's current action - the key is whatever the undo stack belongs to, usually a player's UUID.
Several commands add up into one action until "begin" starts a new one, so a whole brush stroke can be undone at once.
"begin" can be given on its own, as "mapdraw record:<key> begin", to open the next action before drawing anything.
Drawing on a different map than the current action's also starts a new action.
Each key keeps its last 15 actions, in memory only: the history is gone after a restart.

Specify "undo:<key>" instead of an id to roll back that key's last action and drop it from the history.
Only the pixels the action itself changed are restored, so other drawing on the same map survives,
unless it was painted over the very same pixels afterwards.

Optionally specify "send" with a list of players to push the map to them immediately.
Without it the change still reaches viewers, but only on the next item frame sync tick
(see "item-frame-cursor-update-interval" in the Paper config, 10 ticks by default).
Related Tags<entry[saveName].created_map> returns the ID of the map created by the 'new:' argument, if used.
<entry[saveName].undone_map> returns the ID of the map rolled back by the 'undo:' argument, if there was anything to undo.
Usage Example
# Use to create a blank off-white canvas and hand it to the player.
- mapdraw new:<player.world> fill color:233,226,208 save:canvas
- give filled_map[map=<entry[canvas].created_map>;map_locked=true]
Usage Example
# Use to put a red blob on a map and show it to the player at once.
- mapdraw id:<[map_id]> dot x:64 y:64 radius:3 color:red send:<player>
Usage Example
# Use to draw an undoable stroke as one action, then take it back.
- mapdraw id:<[map_id]> dot x:10 y:10 radius:1 color:black record:<player.uuid> begin
- mapdraw id:<[map_id]> line x:10 y:10 to_x:40 to_y:20 radius:1 color:black record:<player.uuid>
- mapdraw undo:<player.uuid> send:<player>

NameRun_async
Related Guide Pagehttps://guide.denizenscript.com/guides/basics/run-options.html
Syntaxrun_async [<script>] (path:<name>) (def:<element>|.../defmap:<map>/def.<name>:<value>) (id:<name>) (delay:<value>)
Short DescriptionRuns a script in a new async queue.
Full DescriptionRuns a script in a new async queue.

You must specify a script object to run.

Optionally, use the "path:" argument to choose a specific sub-path within a script.

Optionally, use the "def:" argument to specify definition values to pass to the script,
the definitions will be named via the "definitions:" script key on the script being ran,
or numerically in order if that isn't specified (starting with <[1]>).

Alternately, use "defmap:<map>" to specify definitions to pass as a MapTag, where the keys will be definition names and the values will of course be definition values.

Alternately, use "def.<name>:<value>" to define one or more named definitions individually.

Optionally, use the "delay:" argument to specify a delay time before the script starts running.

Optionally, specify the "id:" argument to choose a custom queue ID to be used.
If none is specified, a randomly generated one will be used. Generally, don't use this argument.

The run command is ~waitable. Refer to Language:~waitable.
Related Tags<entry[saveName].created_queue> returns the queue that was started by the run command.

- run_async MyTask

NameBrigadier Command Script Containers
DescriptionLike a 'command' script container, but the command is built on Brigadier, the same system vanilla commands use.
The client knows the whole command tree, so it highlights each argument as it is typed, marks invalid input red
before it is sent, shows tooltips on suggestions, and accepts selectors and relative coordinates natively.
The command also works inside '/execute as ... at ... run'.

The container itself is the root literal: its 'script' key runs for the bare command, and 'then' holds the nodes after it.
Every node under 'then' is either a literal (a fixed word) or, if it has a 'type' key, an argument.
A node can have these keys:
- type: the argument type, see Language:Brigadier Argument Types. Leave it out for a literal.
- permission: the permission needed to see and use this node (and everything below it).
- script: runs when the input ends at this node.
- suggest: for arguments only. Either a tag returning a list (or a map of value to tooltip),
or a script section that does 'determine' with such a list/map. A script section may use waits and ~waitable
commands (like ~webget): the client simply gets the suggestions once the queue finishes.
Suggestions are filtered by what is typed so far automatically.
- then: the child nodes.
Argument types can have extra keys, like 'min' and 'max' for numbers.

Inside 'script', every argument on the way to the node is available as <context.(argument name)>, already converted
to a Denizen object (a players argument becomes a ListTag of PlayerTags, a block_position becomes a LocationTag, etc).
Other context: <context.alias> (the label used), <context.raw_args> (everything after the label), <context.source_type>
(player, command_block, command_minecart, entity or server), <context.server> (true if not run by a player),
<context.location> (where the command runs, changed by 'execute at/positioned'),
and <context.executor> (the entity it runs as, changed by 'execute as').
The linked player is the executor when that is a player, otherwise the sender when that is a player.
'determine' a number to set the command result (as seen by 'execute store result').

Inside a 'suggest' tag or script, arguments typed before the current one are available the same way,
plus <context.current> - the text typed so far for the current argument.

'permission' is the only access check: Paper sends the command tree from another thread, where script tags can't run.
Commands update for online players on '/ex reload'.

NameDialog Script Containers
DescriptionDialog script containers define native client-side dialog windows (Paper's dialog API).
Show one with Command:showdialog or Mechanism:PlayerTag.show_dialog.

Each dialog requires a 'base' section with a 'title' and a 'type'.

TYPES:
- confirm : Two-button confirmation dialog, uses 'yes:' and 'no:'
- notice : Simple dialog with a single 'button:'
- list : Shows buttons that open other dialog scripts, listed under 'dialogs:'
- multi : Grid of action buttons, listed under 'buttons:'

'base.after action' decides what happens after a button is clicked: 'close' (default), 'none' (stay open)
or 'wait_for_response' (stays open until the server shows another dialog or closes it).

Every tag in the container is parsed when the dialog is shown, for the player it is shown to,
with the definitions passed to the command (and the definitions of the queue that showed it).
Button 'script' sections run when clicked, with the same definitions.
'condition' on an input, body or button hides it unless the tag returns true.

DYNAMIC GENERATION (Procedural):
A 'procedural' script section at the root of the container runs when the dialog is shown,
and can 'determine' maps for 'inputs', 'bodies' or 'buttons'. Their entries are added on top of
(and replace same-named) entries of the static section.
Tags inside 'script' keys and '<context.inputs...>' tags are escaped automatically when the script loads,
so inside 'procedural' they are only parsed when the button is clicked.

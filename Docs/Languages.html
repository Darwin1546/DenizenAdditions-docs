NameBrigadier Argument Types
DescriptionThe 'type' values available to arguments in Language:Brigadier Command Script Containers,
and what each one becomes in <context.(argument name)>.

Text:
- word: a single word (no spaces). ElementTag.
- string: a single word, or "a quoted phrase". ElementTag.
- greedy: everything until the end of the input. Must be the last argument. ElementTag.
- text: a JSON text component, as in /tellraw. ElementTag of Denizen formatted text.

Numbers ('min' and 'max' keys are optional and checked by the client):
- integer, long, float, double: ElementTag(Number).
- bool: true or false. ElementTag(Boolean).

Game objects:
- player: one player, by name or a single-player selector. PlayerTag.
- offline_player: any player that ever joined, online or not, by name. No selectors.
Suggests names by itself, unless the node has its own 'suggest': online players first, then recently seen ones
(the server's usercache - 'user-cache-size' in spigot.yml), up to 100. Players beyond that are still accepted when typed. PlayerTag.
An unknown name fails with the vanilla "Unknown player" error pointing at the argument, even if later arguments are missing.
- players: any number of players, by name or selector. ListTag(PlayerTag).
- entity: one entity, by selector or UUID. EntityTag.
- entities: any number of entities. ListTag(EntityTag).
- block_position: block coordinates, with ~ and ^ support. LocationTag.
- position: exact coordinates, with ~ and ^ support. LocationTag.
- angle: a yaw angle, with ~ support. ElementTag(Decimal).
- block_state: a block with optional states, like oak_stairs[facing=north]. MaterialTag.
- item: an item with optional components, like diamond_sword[damage=5]. ItemTag.
- world: a world (dimension) key. WorldTag.
- gamemode: a game mode name. ElementTag.
- color: a named chat color, like 'red'. ElementTag.
- hex_color: a hex color, like 'FF0000'. ColorTag.
- uuid: a UUID. ElementTag.
- key: a namespaced key, like 'minecraft:stone'. ElementTag.
- duration: a duration in Denizen's format, like '5s', '1.5h' or '30' (seconds). Units: t, s, m, h, d, w, y.
'infinite' is accepted too and, as everywhere in Denizen, is just a zero duration.
Suggests '1t' to '1y' and 'infinite' while empty, then the units once a number is typed.
Optional 'min' key, also a duration like '1s' - any min above zero rejects 'infinite' as well. DurationTag.
- time: a duration in the vanilla format, like '5s', '2d' or '100' (ticks). Units: t, s, d. Optional 'min' key, in ticks. DurationTag.
- resource: an entry of a registry, chosen with the 'registry' key (like 'enchantment', 'biome', 'entity_type',
or a full registry name like 'worldgen/biome'). The client suggests every entry. ElementTag of its key.

NameBrigadier Command Script Containers
DescriptionLike a 'command' script container, but the command is built on Brigadier, the same system vanilla commands use.
The client knows the whole command tree, so it highlights each argument as it is typed, marks invalid input red
before it is sent, shows tooltips on suggestions, and accepts selectors and relative coordinates natively.
The command also works inside '/execute as ... at ... run'.

The container itself is the root literal: its 'script' key runs for the bare command, and 'then' holds the nodes after it.
Every node under 'then' is either a literal (a fixed word) or, if it has a 'type' key, an argument.
A node can have these keys:
- type: the argument type, see Language:Brigadier Argument Types. Leave it out for a literal.
- permission: the permission needed to see and use this node (and everything below it).
- script: runs when the input ends at this node.
- suggest: for arguments only. Either a tag returning a list (or a map of value to tooltip),
or a script section that does 'determine' with such a list/map. A script section may use waits and ~waitable
commands (like ~webget): the client simply gets the suggestions once the queue finishes.
Suggestions are filtered by what is typed so far automatically.
- then: the child nodes.
Argument types can have extra keys, like 'min' and 'max' for numbers.

Inside 'script', every argument on the way to the node is available as <context.(argument name)>, already converted
to a Denizen object (a players argument becomes a ListTag of PlayerTags, a block_position becomes a LocationTag, etc).
Other context: <context.alias> (the label used), <context.raw_args> (everything after the label), <context.source_type>
(player, command_block, command_minecart, entity or server), <context.server> (true if not run by a player),
<context.location> (where the command runs, changed by 'execute at/positioned'),
and <context.executor> (the entity it runs as, changed by 'execute as').
The linked player is the executor when that is a player, otherwise the sender when that is a player.
'determine' a number to set the command result (as seen by 'execute store result').

Inside a 'suggest' tag or script, arguments typed before the current one are available the same way,
plus <context.current> - the text typed so far for the current argument.

'permission' is the only access check: Paper sends the command tree from another thread, where script tags can't run.
Commands update for online players on '/ex reload'. 

Brigadier_Command_Script_Name:

    type: brigadier_command

    # The name of the command, as in '/warp'.
    name: warp

    # | Optional
    aliases:
    - w

    # | Optional. Needed for the whole command.
    permission: myserver.warp

    # | Optional. Runs for the bare '/warp'.
    script:
    - narrate "Usage: /warp tp <&lt>name<&gt> [players]"

    then:
        # A literal: '/warp set ...'
        set:
            permission: myserver.warp.set
            then:
                # An argument: it has a 'type'.
                name:
                    type: word
                    script:
                    - flag server warps.<context.name>:<player.location>
        tp:
            then:
                name:
                    type: word
                    # A map gives each suggestion a tooltip.
                    suggest: <server.flag[warps].parse_value_tag[<[parse_value].simple>]>
                    script:
                    - teleport <player> <server.flag[warps.<context.name>]>
                    then:
                        targets:
                            type: players
                            permission: myserver.warp.others
                            script:
                            - teleport <context.targets> <server.flag[warps.<context.name>]>
        give:
            then:
                amount:
                    type: integer
                    min: 1
                    max: 64
                    # A script section can wait for anything before answering.
                    suggest:
                    - ~webget https://example.com/amounts save:request
                    - determine <entry[request].result.split[,]>
                    script:
                    - give stone quantity:<context.amount>

NameDialog Buttons
DescriptionButtons define interactive actions within dialogs.

Button sections depend on the dialog type:
- confirm: 'yes:' and 'no:'
- notice: 'button:'
- multi: 'buttons:' (a section of buttons)
- list and multi: 'exit button:'

Button fields:
- label: <text> (Required)
- tooltip: <text>
- width: <number>
- type: SCRIPT (default), RUN_COMMAND, OPEN_URL, COPY_TO_CLIPBOARD

ACTION TYPES:

SCRIPT
Runs the 'script' section when clicked, linked to the player who clicked.
Script buttons only work in the dialog shown last to the player, and with 'after action: close' only for one click.
Showing the player another dialog, Mechanism:PlayerTag.close_dialog or quitting disables them.
Input values are checked against the inputs as they were sent (text length, number range and step, offered options),
and the click is ignored if they don't fit.
Note that the server isn't told when the player closes a dialog with escape or with a non-script button,
so until one of the above happens a modified client can still send one click.
Available context:
<context.button_id> returns the name of the clicked button.
<context.inputs> returns a MapTag of all input values.
<context.(input key)> returns the value of that input.

RUN_COMMAND
Makes the player run a command.
command: spawn

OPEN_URL
Opens a web URL.
url: https://example.com

COPY_TO_CLIPBOARD
Copies text to the player's clipboard.
text: Hello world

NameDialog Inputs
DescriptionDialog inputs collect player data that becomes available to button scripts.

Input values can be accessed directly using <context.(key)> (e.g., <context.applicant_name>),
or as a full map using <context.inputs>.
The key is the input's name in the 'inputs' section, unless 'key' sets another one.

TYPES:

TEXT
A text input field.

- type: text
- label: <text> (Required)
- key: <context_key>
- initial: <text>
- width: <number>
- max length: <number>
- label visible: true/false

Multiline options:
- multiline options:
max lines: <number>
height: <number>


BOOLEAN
A toggle switch input.

- type: boolean
- label: <text> (Required)
- key: <context_key>
- initial: true/false
- on true: <text>
- on false: <text>


NUMBER
A numeric range slider.

- type: number
- label: <text> (Required)
- key: <context_key>
- start: <float> (Required)
- end: <float> (Required)
- initial: <float>
- step: <float>
- width: <number>
- label format: <text>
Example: "Value: %s"


SINGLE
A single-choice selection list.

- type: single
- label: <text> (Required)
- key: <context_key>
- label visible: true/false
- width: <number>

Options:

option_name:
id: unique_id
display: <text>
initial: true/false

NameDialog Script Containers
DescriptionDialog script containers define native client-side dialog windows (Paper's dialog API).
Show one with Command:showdialog or Mechanism:PlayerTag.show_dialog.

Each dialog requires a 'base' section with a 'title' and a 'type'.

TYPES:
- confirm : Two-button confirmation dialog, uses 'yes:' and 'no:'
- notice : Simple dialog with a single 'button:'
- list : Shows buttons that open other dialog scripts, listed under 'dialogs:'
- multi : Grid of action buttons, listed under 'buttons:'

'base.after action' decides what happens after a button is clicked: 'close' (default), 'none' (stay open)
or 'wait_for_response' (stays open until the server shows another dialog or closes it).

Every tag in the container is parsed when the dialog is shown, for the player it is shown to,
with the definitions passed to the command (and the definitions of the queue that showed it).
Button 'script' sections run when clicked, with the same definitions.
'condition' on an input, body or button hides it unless the tag returns true.

DYNAMIC GENERATION (Procedural):
A 'procedural' script section at the root of the container runs when the dialog is shown,
and can 'determine' maps for 'inputs', 'bodies' or 'buttons'. Their entries are added on top of
(and replace same-named) entries of the static section.
Tags inside 'script' keys and '<context.inputs...>' tags are escaped automatically when the script loads,
so inside 'procedural' they are only parsed when the button is clicked. 

Dialog_Script_Name:
    type: dialog

    # Names the definitions passed with 'showdialog ... def:'.
    definitions: target

    base:
        title: <yellow>Main Menu
        type: multi

        # Optional window settings
        external title: App Title
        can close with escape: true
        after action: close

        # Layout columns (list or multi)
        columns: 3

        # Button width (only for 'list')
        button width: 100

    # Exit button (list or multi)
    exit button:
        label: Exit

    # Procedural queue to generate elements dynamically
    procedural:
    - repeat 15 as:x:
        - definemap button:
            label: <[x]>
            width: 15
            script:
            - announce "Clicked button <context.button_id>"
        - define buttons.<[x]>:<[button]>
    - determine buttons:<[buttons]>

    # only for 'list'
    dialogs:
    - other_dialog_script

    # Static content displayed in the dialog
    bodies:
        my_text:
            type: message
            message: Hello, <player.name>!

    # Input fields
    inputs:
        1:
            type: text
            key: custom_context_name
            label: Name
        my_input:
            type: text
            label: Name2

    # Interaction buttons
    # 'multi' uses 'buttons:'
    # 'confirm' uses 'yes:' and 'no:'
    # 'notice' uses 'button:'
    buttons:
        submit:
            label: Submit
            script:
            - narrate "Context is <context.custom_context_name>, <context.my_input>, target is <[target]>"


See also Language:Dialog Inputs, Language:Dialog Buttons and Language:Dialog Bodies.

NameItem Script Containers
DescriptionItem script containers are an easy way to pre-define custom items for use within scripts. Item
scripts work with the ItemTag object, and can be fetched with the Object Fetcher by using the
ItemTag constructor ItemTag_script_name. Example: - drop <player.location> super_dooper_diamond

The following is the format for the container. Except for the 'material' key (and the dScript
required 'type' key), all other keys are optional. 

# The name of the item script is the same name that you can use to construct a new
# ItemTag based on this item script. For example, an item script named 'sword_of_swiftness'
# can be referred to as simply 'sword_of_swiftness'.
Item_Script_Name:

    type: item

    # Must be a valid ItemTag. See 'ItemTag' for more information.
    # | All item scripts MUST have this key!
    material: base_material

    # List any mechanisms you want to apply to the item within
    # | Some item scripts should have this key!
    mechanisms:
      # An example of a mechanism to apply
      unbreakable: true
      # Other common example
      custom_model_data: 5
      # This demonstrates how to add a custom attribute modifier.
      attribute_modifiers:
          # One subkey for each attribute you want to modify.
          # Valid attribute names are listed at https://hub.spigotmc.org/javadocs/spigot/org/bukkit/attribute/Attribute.html
          generic_armor:
              # Each attribute can have a list of modifiers, using numbered keys. They will be applied in numeric order, low to high.
              1:
                  # Each modifier requires keys 'operation' and 'amount', and can optionally have keys 'name', 'slot', and 'id'.
                  # Operations can be: ADD_NUMBER, ADD_SCALAR, and MULTIPLY_SCALAR_1
                  operation: add_number
                  amount: 5
                  # Slots can be: HAND, OFF_HAND, FEET, LEGS, CHEST, HEAD, ANY
                  slot: head
                  # ID is a UUID used to uniquely identify modifiers. If unspecified the ID will be randomly generated.
                  # Items with modifiers that lack IDs cannot be stacked due to the random generation.
                  id: 10000000-1000-1000-1000-100000000000

    # The 'custom name' can be anything you wish. Use color tags to make colored custom names.
    # | Some item scripts should have this key!
    display name: custom name

    # Lore lines can make items extra unique. This is a list, so multiple entries will result in multiple lores.
    # If using a replaceable tag, they are filled in when the item script is given/created/dropped/etc.
    # | Some item scripts should have this key!
    lore:
    - item
    - ...

    # If you want an item to be damaged on creation, you can change its durability.
    # | Most item scripts should exclude this key!
    durability: 12

    # Each line must specify a valid enchantment name.
    # | Some item scripts should have this key!
    enchantments:
    - enchantment_name:level
    - ...

    # Set this to 'true' to allow the item script item to be used in material-based recipe (eg most vanilla recipes).
    # Defaults to false if unspecified.
    # | Most item scripts should exclude this key!
    allow in material recipes: false

    # You can specify flags to be added to the item.
    flags:
      # Each line within the flags section should be a flag name as a key, and the flag value as the value.
      # You can use lists or maps here the way you would expect them to work.
      my_flag: my value

    # You can optionally add crafting recipes for your item script.
    # Note that recipes won't show in the recipe book when you add a new item script, until you either reconnect or use the "resend_recipes" mechanism.
    # | Most item scripts should exclude this key, unless you're specifically building craftable items.
    recipes:
        1:
            # The type can be: shaped, shapeless, stonecutting, furnace, blast, smoker, campfire, or smithing.
            # | All recipes must include this key!
            type: shaped
            # The recipe can optionally have a custom internal recipe ID (for recipe books).
            # If not specified, will be of the form "<type>_<script.name>_<id>" where ID is the recipe list index (starting at 1, counting up).
            # IDs will always have the namespace "denizen". So, for the below, the full ID is "denizen:my_custom_item_id"
            # Note that most users should not set a custom ID. If you choose to set a custom one, be careful to avoid duplicates or invalid text.
            # Note that the internal rules for Recipe IDs are very strict (limited to "a-z", "0-9", "/", ".", "_", or "-").
            # | Most recipes should exclude this key.
            recipe_id: my_custom_item_id
            # You can optionally add a group as well. If unspecified, the item will have no group.
            # Groups are used to merge together similar recipes in the recipe book (in particular, multiple recipes for one item).
            # | Most recipes should exclude this key.
            group: my_custom_group
            # You can optionally specify the quantity to output. The default is 1 (or whatever the item script's quantity is).
            # | Only some recipes should have this key.
            output_quantity: 4
            # You must specify the input for the recipe. The below is a sample of a 3x3 shaped recipe. Other recipe types have a different format.
            # You are allowed to have non-3x3 shapes (can be any value 1-3 x 1-3, so for example 1x3, 2x1, and 2x2 are fine).
            # For an empty slot, use "air".
            # By default, items require an exact match. For a material-based match, use the format "material:MaterialNameHere" like "material:stick".
            # Item script items in shaped and shapeless recipes are the exception on Paper 26 and newer: they match by the item script they come from, so a renamed or otherwise modified item still counts.
            # To make multiple different items match for any slot, just separate them with slashes, like "stick/stone".
            # To match multiple materials, use "material:a/b/c".
            # You can also make a dynamic matcher using '*', like "material:*_log" to match any log block,
            # or 'test_*' to match any item script that has name starting with 'test_'.
            # Note that to require multiple of an item as an input, the only option is to use multiple slots.
            # A single slot cannot require a quantity of items, as that is not part of the minecraft recipe system.
            # | All recipes must include this key!
            input:
            - ItemTag|ItemTag|ItemTag
            - ItemTag|ItemTag|ItemTag
            - ItemTag|ItemTag|ItemTag
       # You can add as many as you want.
       2:
            # Sample of the format for a 2x2 recipe
            type: shaped
            input:
            - ItemTag|ItemTag
            - ItemTag|ItemTag
       3:
           # Shapeless recipes take a list of input items.
           type: shapeless
           # Optionally specify the shapeless category for shapeless recipes, as "building", "redstone", "equipment", or "misc". Defaults to "misc" if unspecified.
           # | Only some recipes should have this key.
           category: misc
           input: ItemTag|...
       4:
           # Stonecutting recipes take exactly one input item.
           type: stonecutting
           input: ItemTag
       5:
           # Furnace, blast, smoker, and campfire recipes take one input and have additional options.
           type: furnace
           # Optionally specify the cook time as a duration (default 2s).
           # | Only some recipes should have this key.
           cook_time: 1s
           # Optionally specify the cooking category for cooking recipes, as "food", "blocks", or "misc". Defaults to "misc" if unspecified.
           # | Only some recipes should have this key.
           category: misc
           # Optionally specify experience reward amount (default 0).
           # | Only some recipes should have this key.
           experience: 5
           input: ItemTag
       6:
           # Smithing recipes take one base item and one upgrade item.
           # In versions 1.20 and up, smithing recipes take one template item, one base item, and one upgrade item.
           type: smithing
           template: ItemTag
           base: ItemTag
           # Optionally, choose what values to retain, as a simple pipe-separated list of parts to retain.
           # If unspecified, no values will be retained.
           # Parts can be: 'display', 'enchantments'
           retain: display|enchantments
           upgrade: ItemTag

       7:
           # Brewing recipes take one base item and one ingredient item.
           # | Brewing recipes are only available on Paper versions 1.18 and up.
           # | Brewing recipes also have a special input option on 1.20 and above: "matcher:<item matcher>", to allow advanced matchers on the input/ingredient items.
           type: brewing
           input: ItemTag
           ingredient: ItemTag

    # Set to true to not store the scriptID on the item, treating it as an item dropped by any other plugin.
    # NOTE: THIS IS NOT RECOMMENDED UNLESS YOU HAVE A SPECIFIC REASON TO USE IT.
    # | Most item scripts should exclude this key!
    no_id: true/false

    # If your material is a 'written_book', you can specify a book script to automatically scribe your item
    # upon creation. See 'book script containers' for more information.
    # | Most item scripts should exclude this key, though there are certain rare cases it may be useful to.
    book: book_script_name
